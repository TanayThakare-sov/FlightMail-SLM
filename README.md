FlightMail-SLM: Airline Email to Structured Data

Fine-tunes a small language model (Qwen2.5-0.5B-Instruct) with LoRA to read airline delay and cancellation emails and extract the booking details as JSON.

Problem

When a flight is delayed or cancelled, the airline sends an email. Every airline writes these emails differently, and travel agents often read them and re-type the details into their own system by hand. This is slow and error-prone. This project tests whether a small, fine-tuned language model can do the extraction automatically.

Input (email):

Hi Vikram Sharma, quick update. Your HYD to MAA flight (6E9039) on 01 Aug 2026 now leaves at 18:40 instead of 16:40. Ref: 49Z4BL.

Output (JSON):

json
{"event_type": "schedule_change", "passenger": "Vikram Sharma", "pnr": "49Z4BL",
 "flight_no": "6E9039", "origin": "HYD", "destination": "MAA",
 "date": "01 Aug 2026", "old_time": "16:40", "new_time": "18:40"}
Data (synthetic)

Real airline emails are private, so all data is generated by make_fake_emails.py (random names, booking codes, flights, dates and times).

Train: 1,000 emails in 3 airline writing styles.
Test: 200 emails in 3 styles. Only 1 style was seen in training; 2 styles are new. This checks whether the model works on formats it has not seen.

Because the data is synthetic and template-based, results here are cleaner than real-world emails would give. Real emails would be messier and scores would likely be lower.

Method
Base model: Qwen/Qwen2.5-0.5B-Instruct
Fine-tuning: LoRA (r=16, alpha=32) on attention layers, 2 epochs, learning rate 2e-4. Only 2,162,688 of 496,195,456 parameters (0.44%) are trained.
Training was run on a free Google Colab T4 GPU.
Compared three systems on the same test set:
Regex: hand-written rules (regex_baseline.py), written by looking at the training styles only.
Base model: Qwen2.5-0.5B-Instruct with no training (prompted to return JSON).
Fine-tuned: base model + LoRA adapter.

Notes on the table:

The base model's 0% JSON validity may partly reflect the plain prompt used (no chat template), so this comparison may be unfair to the base model. Its 49.5% on new_time is not real skill: for cancellations the correct value is empty, and an empty output matched by chance.
Fine-tuning clearly improved booking code, passenger name and route extraction on new email styles, and raised full-record accuracy from 31.5% to 45.5%.
45.5% fully correct is modest. The model is not production-ready.
Error analysis

Mistakes are saved in errors.jsonl (email, expected answer, model output, wrong fields). In the examples inspected, the main failure was cancellation detection on unseen wording:

All 3 training styles used the word "cancelled", so emails saying "CNX" or "will not operate" were labelled schedule_change instead of cancellation. This is why event_type accuracy (65.5%) did not improve over the regex baseline.
The other fields (booking code, name, route, date) were usually still extracted correctly in those emails.
A smaller error: the model sometimes copied extra text into a time field, for example "05:50 hrs." instead of "05:50", when the email format differed from training.
Limitations
Synthetic, template-based data; only a few email styles; two event types.
Single training run, single test set, no repeated runs, so no confidence intervals.
Error analysis is based on the sample of errors inspected, not a full categorisation.
Next steps
Add more cancellation wordings and time formats to the training data, then retrain and re-test.
Evaluate with a proper chat template for the base model.
Try real (permitted) emails and more event types (gate change, delay, rebooking).
How to run
pip install -r requirements.txt
python make_fake_emails.py     # creates train.jsonl and test.jsonl
python regex_baseline.py       # regex baseline only (no GPU needed)
python train.py                # needs a GPU (for example free Google Colab T4); creates lora_out/
python evaluate.py             # prints the results table, creates results.json and errors.jsonl
Files
